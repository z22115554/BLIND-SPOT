# 設計審閱筆記：原企劃（Gemini 生成提示詞）的問題與處理方式

企劃整體方向很完整，但逐條實作時發現一些**互相矛盾、技術上不可行、或劇情邏輯有缺口**的地方。
下面列出每一點、我採取的處理，以及仍需要你決定的開放問題。所有文字都集中在 `src/data/script.js`，
標記【補充文案】的都可以直接改。

---

## A. 規格之間的矛盾

### A1.「嚴禁畫面閃爍」 vs 「車燈一閃而過」「濃煙瞬間湧入」「雪花雜訊」
「一閃而過的刺眼車燈」與「瞬間湧入」字面上就是突發的亮度/畫面劇變，正好是零跳臉與光敏感族群要避免的東西；
監視器的雪花雜訊本質上也是高頻閃爍。

**處理**：
- 車燈改為「掃過」：0.6 秒以上漸亮、約 1 秒以上漸暗，整段 2.5–3 秒，重點放在**牆上被拉長的影子**而不是強光本身。
- 濃煙用約 7 秒「翻湧著吞沒」房間，不是一瞬間。
- 雪花雜訊低對比、平均亮度固定；另外提供**光敏感模式**（標題/暫停畫面可切換），雜訊改為緩慢流動、關閉頭部擺動與色差。
- 全域規則：任何亮度變化 ≥ 0.4 秒；0.25 秒內整體亮度變化 ≤ 30%；不穩燈管只做緩慢、≤15% 的起伏。

### A2.「雕像般絕對靜止」 vs 第三幕「正拼命想撬開防爆門」
第一幕要求人影被看著時絕對靜止；第三幕高清畫面卻描述他在拼命破門。

**處理**：低畫質（第一幕）嚴格遵守盲區規則；**高清（第三幕）他會動**——緩慢、筋疲力竭地揮斧劈門，並在主控室裡聽到隔門的悶響。
「被看著就不動」被重新詮釋為主角妄想的一部分：恢復真實畫面的那一刻，他其實一直是個活生生、正在救人的人。
（若你偏好第三幕也靜止，在 `RevelationState` 把 `setHDAction(true)` 拿掉即可。）

### A3. 人影「推進」與對講機時間軸會不同步
若玩家整段第一幕都盯著 CAM-03，人影永遠不會動；但 02:13 對講機卻說「我要破門了」——畫面與聲音會穿幫。
反過來，若玩家一直移開視線，人影可能 02:02 就到門口了。

**處理**：時鐘採「節拍閘門」：每一個劇情事件（02:03 / 02:05 / 02:08 / 02:13）時鐘會停住直到玩家完成它；
每個節拍設定人影推進的**上下限**。對講機刻意放在**防爆門旁的西牆**（門鈴的位置，也正是門外那個人的聲音來源），
接聽時一定要轉身背對監視器 → 人影一定會在玩家不看時補上進度。另外規定：人影只有在「先被你看見、你再移開視線」之後才推進，
所以每一次推進玩家都會察覺到。

**補充（節奏改版，見 E）**：02:00 多了一個閘門——玩家親手把防爆門鎖死。上下限表 `GATE_LIMITS` 完全不變（搬到
`monitoringDirector.js` 與 node 模擬共用）；鎖門閘門開始前先設 {0,2}，所以第一次轉身去鎖門就會讓人影走一步。
人影依然只在「先被看見、再移開視線」之後推進；上限內多了一次性的細微「次姿勢」（E2），不改 index，不影響心跳與 A3。

### A4. 「Frustum Culling」字面上不足以判定「玩家正在看」
Three.js 的 frustum culling 是渲染最佳化；而且監視器攝影機本身永遠「看得到」人影，真正重要的是**玩家有沒有在看那台 CRT**。
單純的視錐相交太寬鬆（螢幕在畫面邊角也算）。

**處理**：`GazeSystem` 同時要求：視錐相交（`Frustum.intersectsBox`）＋視線中央 34° 錐＋距離＋射線遮蔽（被門牆擋住不算）
＋螢幕正面朝向＋沒有在檢視物品＋沒有切到別的頻道。

## B. 劇情/空間邏輯缺口

### B1. 兩條「維修廊道」會撞在一起
CAM-03 拍的是「公務維修廊道 B區」，第三幕又說 CAM-03 在「防爆門外」；第二幕玩家要「進入地下公務維修廊道」。
如果是同一條廊道，玩家第二幕就會跟人影正面相遇（而且會變成貼臉驚嚇）。

**處理**：拆成兩條——
- **西牆防爆門 → B 區廊道**（CAM-03 拍攝處，人影/消防員所在，玩家永遠進不去）。
- **東牆側門 → 地下公務維修廊道**（第二幕路線，通往電閘室）。

### B2. 02:03 他說「門……打不開」，但畫面上他還在廊道遠端
日誌寫「02:05 有人在敲防爆門」，對講機 02:03 他已經在說門打不開，可是 CAM-03 前期畫面裡他還在很遠的地方。
**詮釋**：低畫質畫面裡「逐漸逼近」本身就是主角的扭曲知覺；高清畫面揭露他**其實一直就在門口**。這反而強化了反轉，
所以保留原文、不做修改。

### B3. 真相揭露的文本不夠
企劃說第三幕「對講機傳來清晰錄音，揭露三年前的真相：……鎖死防爆門並切斷通風……」，
但階段四錄音的實際台詞只有求救，**沒有**說出「鎖門」「切斷通風」「兩人都死了」這些事實。

**處理（【補充文案】）**：
- 右側機電螢幕在高清後顯示「通風：主排風 手動切斷（02:05 操作員）」——第一幕玩家「重啟通風」的動作，被揭露其實是切斷。
  （原本寫 02:11，與玩家 02:05 拉下拉桿的時間對不上；節奏改版時把兩處【補充文案】改成 02:05，見 E3。
  左螢幕事故摘要同樣改為「02:05 主排風遭控制室內手動切斷。」，緊接在「02:05 救援隊員抵達……」之後。）
- 左側螢幕顯示「事故調查摘要（三年前）」：救援隊員於防爆門外殉職、值班員於室內窒息、防爆門由內部反鎖。

### B4.「寫下最後一句話」沒有指明是哪一句
**處理**：解讀為便利貼的最後一句「**鎖死防爆門。**」——便利貼是主角寫給下一輪自己的訊息（呼應日誌「字跡一模一樣」），
終幕畫面中便利貼已寫好大半，筆寫下最後一句。循環每多一次，便利貼角落多一道「正」字記號。

### B5.「每次玩家從廊道返回主控室」——正常流程只會返回一次
**處理**：復電前每次折返主控室都會累加一次腐化（最多 0.45）；復電後回來直接跳到明顯陳舊（≥0.6），聽完錄音再到 0.85，終幕焦黑。

## C. 技術限制

| 問題 | 處理 |
|---|---|
| 「模組化」與「貼上即可執行」衝突：ES modules 無法從 `file://` 載入，CDN 又算外部依賴 | 原始碼模組化（`src/`），以 esbuild 打包成**單一自足 HTML**（three.js 內嵌、零外部請求），雙擊即可玩 |
| 瀏覽器自動播放政策：Web Audio 必須由使用者點擊啟動 | 標題畫面「點擊開始交接」，同一次點擊啟動音訊與指標鎖定 |
| Pointer Lock 在部分 iframe/瀏覽器不可用 | 自動退回「按住左鍵拖曳環顧」模式（Esc 一樣可以暫停） |
| 企劃指定 `PointerLockControls` | 用的是同一套瀏覽器 Pointer Lock API，但改由自製 `PlayerController` 管理視角：甦醒起身、轉頭看門、坐下/趴倒這些**劇本運鏡**需要獨立的 yaw/pitch/roll 狀態與補間，`PointerLockControls` 會直接改寫相機旋轉而且沒有拖曳退回模式。手感（滑鼠靈敏度、俯仰上限）等同 |
| Web Audio 無法程式化合成**聽得懂的中文語音** | 對講機用共振峰濾波噪音合成「像人聲的呢喃」＋喘息/敲擊/咳嗽/斧頭聲，配逐段累加的字幕；字幕最終字串與原文逐字相同。之後若有錄音可直接替換 |
| 不能載入網路字型 | Canvas 與 UI 用系統字型堆疊；便利貼/日誌手寫字優先用系統楷體（標楷體/楷體），沒有時退回一般字型並加逐字抖動模擬手寫 |
| 「降低環境光源色溫」 | 依字面實作：色溫降低＝由冷白日光燈 (≈6500K) 變成髒琥珀色 (≈3000K)，同時也預示火災。若你原意是「變冷/變藍」，改 `ControlRoom` 的目標色即可 |

## D. 需要你決定的開放問題

1. **錶的主人是誰？** 「給阿哲，值夜班注意安全」——「值夜班」指向值班員（主角＝阿哲），但錶卻在主角從未去過的維修廊道排水溝旁。
   - 若要明確是**主角的**：把錶移到主控室（例如椅子下）。
   - 若要明確是**消防員的**：把「值夜班」改成「出勤」。
   - 目前保留原文的曖昧（兩種讀法都成立：救援者的錶停在 02:14:08，恰是跳電/濃煙倒灌的那一刻）。
2. **電閘室的雨衣屬於誰？** 高清畫面中消防員身上穿著外套，那鐵架上這件是誰的？目前視為同隊隊員/記憶碎片，不影響劇情；
   若想更緊密，可以讓高清畫面中的消防員**沒穿外套**（把外套留在電閘室是為了鑽進狹窄的廊道）。
3. **工作人員名單** 目前是佔位文字（「企劃・劇本・文案：原始企劃案」），請換成實際名單。
4. **監看段落節奏改版**的五個問題（上鎖閘門、02:11 → 02:05、次姿勢、長度、`01:58:41` 與 `▲ CAM-0n`）見 **E6**。

## E. 試玩回饋 → 監看段落（02:00 → 02:14）節奏改版

完整規格：`docs/pacing/spec.md`（三份提案與評審理由在 `docs/pacing/proposal-*.md`，進度在 `docs/pacing/STATUS.md`）。

### E1. 問題
試玩回饋：「氣氛很好，但中段太慢。事件之間應該要看監視器，可是畫面上根本沒有東西不對勁——只有 CAM-03 的人影越來越近，
看過一次就沒事可做了。」量測也證實：舊版這一幕約 4 分 48 秒，其中約 3 分 41 秒什麼都不用做，空檔長達 51 / 34 / 51 / 85 秒，
CAM-01 / 02 / 04 看過一次就永遠不會變。問題不是「太長」，而是「沒事做」。

### E2. 改了什麼、為什麼
- **監視系統的「動態偵測」（VMD）是唯一的新注意力語言**：大約每分鐘一次，某個沒在看的頻道變了——控制台該頻道的 CAM 按鈕
  亮琥珀燈（2.4 秒緩慢呼吸、起伏 ≤ 15%，光敏感模式下恆亮）、一聲輕柔的兩音提示（座位約 −31 dBFS）、CRT 上一行
  `▲ CAM-04`、切過去後 OSD 標籤 `▲ 動態偵測 HH:MM:SS`、SYS LOG 一行、互動提示「切換至 CAM-0n（動態偵測）」。
  注視 1 秒算「已查看」。沒有響鈴、沒有閃爍、沒有新燈光。
- **盲區純度（硬規則）**：頻道只在「沒有被顯示」時換階段（CAM-03 沿用「沒被看著」的規則）；導演排程一次、
  `CameraFeeds.setAnomalyStage` 的防呆再擋一次。畫面上永遠不會「看著它變」。
- **HD 雙生規則**：每個 LD 變化都是第三幕高清真相的一小片，放在同一個座標：號誌 ↓ → ✕／`隧道封閉`（OSD 仍寫「狀態：正常」）、
  車門關上車頂燈熄、拱頂下的黑煙帶、熱源裡的油罐車與車頭剪影、牆上焦痕與三角錐、霧轉為煙＋兩盞路障琥珀燈、
  CAM-04 時間停在 `02:14:08`（唯一的時間異常，無提示）。第三幕從「真相」變成「認出來」。
- **02:00 上鎖閘門**：醒來讀到自己寫的「鎖死防爆門。」，右螢幕寫「防爆門：未鎖定」、門燈是綠的——玩家親手轉氣壓閥手輪鎖門
  （SYS LOG `02:00 防爆門 手動上鎖（操作員）`）。呼應終幕的「解除氣壓門鎖」與事故摘要「防爆門由內部反鎖」。
- **02:05 敲門**：拉下通風拉桿後，玩家看著 CAM-03 時（他還在走廊中段），身後的防爆門傳來三下、再兩下悶悶的敲門聲
  （聲學錯位；從不在玩家距門 2.5 m 內、通話中或檢視中發生）。原企劃日誌「02:05 有人在敲防爆門」因此成真；
  之後檢視防爆門多一句「鋼板摸起來是溫的。」
- **CAM-03 的回報**：人影推進時若玩家沒在看，3–6 秒後 CAM-03 也會出現動態偵測（只有燈與文字，沒有提示音；玩家回來看就取消；
  final 修正：CAM-03 當時就在主螢幕上、玩家人在座位——只是低頭按 CAM 按鈕——時不發，見 E7）——
  「偵測到靜態人形物體」上方掛著「▲ 動態偵測」，這個矛盾就留在畫面上。到達上限的時段，看過再移開會換成一次細微的
  **次姿勢**（額頭抵牆、手掌貼牆、低頭、肩膀垮下、手按胸口、伸出的手垂下；從不更朝向鏡頭；index 6、7 沒有）。
  地上多了一道沿 HD 消防水帶路徑的濕亮拖痕，只在他走一步時延長。
- **輕量注意力時鐘**：非保護分鐘在「沒事可做」時提早翻（最少 11 秒；OSD 秒數 1 秒內跑到 :59 再翻，秒數永不倒退），
  最長仍是 17 秒（＝舊版）。**02:10、02:11、02:12 永不縮短**（通風衰弱與 02:12 的聽覺真空長度不動）。
  02:00 上鎖閘門完成後約 4.5 秒就翻到 02:01（final 修正，見 E7）。
- **沒有改的**：閘門結構、`GATE_LIMITS`、「先看見再移開才會動」、所有【原企劃文案】、零跳臉規則。

### E3. 量測結果（整合時）
- node 模擬（`node scripts/pacing-sim.mjs`，每種玩家 200 次）：一般玩家 4:27（p10–p90 4:22–4:33）、積極玩家 4:00、
  只盯 CAM-03 的玩家 5:01、被動玩家 5:23；每次都有 8 個提示、人影最後都在 index 7、敲門都落在 02:05。
- 瀏覽器自動駕駛（`node scripts/pacing-run.mjs`，`?speed=4`）與舒適度量測的數字見 `docs/pacing/STATUS.md`。
- 最長「沒有新事件」的空檔約 18–20 秒，刻意落在 02:10 通風衰弱那一分鐘；02:12 的真空是刻意保留的。

### E4. 開關與調整鈕
- `?pace=0`：改版前的流程（沒有導演、輕量時鐘、上鎖閘門、敲門、次姿勢；final 修正後 CAM-03 的濕拖痕也不再隨人影延長），
  可以直接比較。仍與改版前不同的地方：第 0 階段的固定佈景（CAM-01 LD 的門架與放大 1.35 倍的號誌、CAM-04 的車頂燈光暈）、
  第三幕時間戳 02:11 → 02:05 的文案。比較「CAM-03 變化的頻率」時這兩者不影響。
- `?lock=0`：沒有 02:00 上鎖閘門（防爆門一開始就鎖著）。
- `?subposes=0`：關掉 CAM-03 的次姿勢。
- `?spm=N`：每分鐘秒數（`DWELL_MIN` 等比例縮放）；`?seed=N`：導演亂數；`?pacelog=1`：每分鐘一行 `[pace]` 與停電時的摘要表。
- 常數全部在 `src/states/monitoringDirector.js` 的 `PACE`：還嫌慢 → `DWELL_MIN: 9, CALM: 3`（一般玩家約 4:12）；
  太趕 → `DWELL_MIN: 13`（約 4:40）。不要縮短 `PROTECTED`；積極玩家這一幕不要低於 3:45。
- `PACE.RUSH_IN_DWELL`（預設 true）：最早翻分鐘正好落在 11 秒（規格文字的意思）；false 是規格偽碼的字面版本（多約 4 秒）。

### E5. 整合時的調整（與規格數字不同的地方）
- CAM 按鈕琥珀燈的呼吸深度 0.85–1.0（規格寫 0.3–1.0，會超過「≤ 15% 起伏」的規則）；`ControlRoom` 的 `CAM_LED.depth`。
- 提示音與敲門聲的增益（`SFX_GAIN.vmdTone 0.5`、`doorKnock 0.24`）：規格的起始值實測只有 −45 / −42 dBFS，被環境音完全蓋掉；
  調到座位約 −31 / −30 dBFS（上限 −28）。
- 各階段的 `MEAN_SCALE` 改為實測值（`scripts/feed-stages.mjs --write`）：CAM-01 第 2 階段實測 0.40（估計 0.78），
  AGC 依此補償，所以切換進變暗的畫面仍然平順。
- CAM-02 第 1 階段除了煙帶，也把熱源亮斑壓暗（只有煙帶的話，在 CRT 尺寸下 s0 → s1 幾乎看不出來）。final 修正再加強，見 E7。
- CAM-03 拖痕：法線取「鏡頭與盡頭燈的半向量」、粗糙度 0.3——像濕地面一樣反射盡頭那盞燈，才讀得出來
  （平放或朝鏡頭時在 CRT 上完全看不見）。人影在 index 4 時拖痕多半被他自己的身體擋住，index 5–6 才明顯。

## F. 審查修正時刻意偏離原規格的地方

- **車燈事件（第二幕）**：看不見的車從西邊慢慢倒車經過，車燈是帶遮罩的柔邊聚光燈，在玩家前右方的南牆投出一塊窗形光斑，
  玩家被拉長的影子落在光斑裡；整段 4.1–4.7 秒（漸亮 1.7 秒、漸暗 2.0 秒），光敏感模式約 5.5 秒。
  觸發點從 x = 16.5 移到 18.4；手電筒在事件中依朝向調暗（朝東 0.3、朝西 0.85，1.7 秒）。重點仍是牆上的影子，不是強光。
- **終幕濃煙**：開門約 1.35 秒後才開始湧入，先沿天花板翻滾、再往下沉；大部分時間霧約 0.15、濛霧 ≤ 0.6，最後才變濃——
  比原本的「瞬間湧入」更慢（符合 A1）。門內側有一盞橘紅火光（借用既有的補光燈、燈光數量不變），起伏 ≤ 9%、週期 ≥ 1.9 秒，
  光敏感模式下恆定。終幕約比之前長 2 秒。
- **手電筒開關 1.1 秒**（光敏感模式 1.6 秒）：比原本約 0.8 秒的設計慢，因為低於約 0.85 秒就做不到「0.25 秒內 ≤ 30%」。
- **多出來的一步改為必定發生**：走動 ≥ 0.4 秒後停下，一定會多一步（原本是機率）。這是聲學錯位的核心，不能靠運氣。
- **通風停止改為快速停機**：40 秒的變調衰弱不變，最後 0.6 秒轉速掉光＋0.7 秒的停機聲，0.8 秒內被抽成真空——
  要被感覺成「一個洞」，不是慢慢淡掉（仍是平滑 ramp，沒有巨響）。
- **終幕只剩一個互動**：解鎖鈕亮起後，其他互動全部停用（原本是「唯一關鍵互動」，現在是「唯一互動」）。
- **咖啡杯移位**：移到左側鍵盤與筆筒之間（x = −0.8），讓杯子與終幕便利貼能在同一個鏡頭裡。
- **坐姿俯仰角改為 0.03**（原本 −0.05）：960×540 與 1280×720 下 02:00 的電子鐘完整入鏡。

## G. 手機／平板（觸控）支援

擁有者的要求：「操作很少，手機應該也能玩」。目標是**同一套遊戲、同一份文案與節奏**，只換輸入方式與畫質；桌機完全不變
（所有觸控樣式都在 `html.bs-touch` 底下，桌機 A/B 截圖逐像素相同）。實作與 API 見 `docs/ARCHITECTURE.md` §4.1。

### G1. 操作的決定
- **環顧＝拖曳畫面**，方向同滑鼠（手指往右＝轉向右，行動 FPS 慣例）。增益＝1.25 × 基本垂直視角 ÷ 視窗短邊 × 靈敏度：
  橫向拖過整個高度約轉 1.25 個垂直視角；直向也用短邊與橫向的視角計算（iPhone SE 直向拖過整個寬度約 88°，
  原本只有 66°，轉身要好幾次）。直接套用、沒有慣性、沒有吸附。
- **移動＝左側浮動搖桿**：拇指落點出現、類比、死區 20%，只有能移動時才出現（左下角有很淡的提示圈）。
  坐著推搖桿＝站起來。搖桿區裡按在可互動物件上（坐著時的 CAM-01 就在搖桿區）時先當作點擊（容差 16 px），
  明確拖動超過 16 px 才變成搖桿——稍微滑動的點擊不會讓玩家站起來。沒有快走（Shift）。
- **互動＝點擊物件**（< 10 px、< 0.45 秒，含 12／24 px 容錯環）；底部互動提示本身是按鈕（直向時靠右下，避開搖桿區）。
  點到 8 m 內、但超出互動距離的物件：淡入【補充文案】「再走近一點」（不觸發、不覆蓋其他提示）。
  點到有動態偵測的 CAM 按鈕：同時淡入「切換至 CAM-0n（動態偵測）」1.6 秒——觸控玩家看不到準心提示，這是色弱玩家的文字線索。
- **湊近看監視器**（final 修正新增）：手機上 CRT 只有約 210 CSS px 寬，動態偵測標籤約 6 px、琥珀燈約 3 px，根本讀不到——
  正好重演「監視器上沒有東西不對勁」。點一下監視器 → 0.8 秒平滑轉向並把垂直視角收窄到 38°（直向：水平視角至少 46°），
  橫向手機約放大 2 倍；再點一下畫面、拖曳、推搖桿、檢視、暫停或切換狀態就 0.8 秒退回。手機畫質另外把 OSD 的
  動態偵測標籤、警示列與狀態標籤放大約 1.3 倍。觸控版的動態偵測提示與操作說明都提到「點監視器：湊近」。
- **暫停＝右上角 ⏸**（44 px 以上的觸控範圍）；檢視物件時隱藏（側邊面板的 ✕ 會緊貼著它）。恢復遊戲後，淡出中的暫停幕
  立刻不再攔截觸控（否則恢復後第一個拖曳會拖到音量滑桿）。
- **直向**：放寬垂直視角讓水平視角至少 62°（上限 100°），控制台與 CRT 仍完整可見。依「這台裝置用過觸控」決定，
  接上鍵盤或碰一下觸控板不會讓視角瞬間跳動。
- **標題**：建議戴耳機、橫向持握；iPhone 請關閉靜音開關（Web Audio 會被靜音開關消音，網頁無法偵測）。
  開始時（同一個手勢內）嘗試全螢幕＋鎖定橫向（Android Chrome）；iPhone 不支援就安靜略過。
- **沒有震動回饋**（震動＝驚嚇）；所有觸控介面的出現/消失 ≥ 0.4 秒；視角的變化都是平滑的。

### G2. 混合裝置（觸控筆電、平板接鍵盤）
- 依最後一次的輸入方式切換；觸控筆只在手機／平板上算觸控（桌機的繪圖板／Surface 筆當作滑鼠，不會整局變成觸控介面）。
- 切換的那個手勢裡，觸控版面延到 click 之後才套用——否則標題的「點擊開始交接」會因為觸控說明出現而往下移，第一次點擊落空。
- 滑鼠指標鎖定中碰螢幕：瀏覽器把這個觸控的座標凍結成 (0,0)；第一個 move 才定起點（原本會一次轉 124° 並低頭看地板），
  單一事件位移超過視窗長邊 30% 一律視為重新起點；旋轉螢幕時放開所有觸控。
- 觸控切回滑鼠時指標還沒鎖定：用既有文案「點擊畫面繼續值班」提示點一下畫面。

### G3. 畫質（`core/quality.js`，只在手機／平板）
像素比上限 1.25、自動解析度門檻較寬（約 < 36 fps 才降、> 52 fps 才升；最多降到 ×0.6）、PCF 陰影、監視器 render target
480×360 無 MSAA、粒子上限（灰燼 480、浮塵 200、濃煙 40）、OSD 動態偵測文字放大。燈光數量（15 盞）與場景內容不變——
這也是手機上最大的風險（每個像素都要算 15 盞燈）。

### G4. 限制（試玩時請留意）
- **真機幀率還沒量過**：這裡只有 SwiftShader 模擬（0–5 fps）。如果手機很卡，先回報機型；可以再降像素比或關陰影。
- iPhone Safari 沒有全螢幕 API 與方向鎖定；iOS 13 以前沒有 Pointer Events（需要 iOS 13+）。
- 很高的手機直向（390×844）會碰到 100° 的視角上限，上下有些透視拉伸；CAM-01／04 在畫面邊緣（仍看得到、點得到）。
- `user-scalable=no` 擋掉頁面縮放（遊戲需要；無障礙上的取捨）。
- 自動化測試的觸控點擊需要 `?tapms=N`（headless 每個觸控事件要等一幀）；這是測試工具的限制，不是遊戲的。
